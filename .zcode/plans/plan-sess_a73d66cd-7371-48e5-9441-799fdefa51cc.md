# 大纲主请求拆分为多步生成(根治长度截断)

## 背景与根因

开题中心 `expandDirection` 的**主请求**(purpose=`outline-expand`)一次性要求模型产出 14 个 `##` 段(定位/驱动/金手指/规模/四幕/卷纲/世界/启动包/支线/故事线/情绪/卖点/角色10个/伏笔10条),体量约 8000-15000 字。推理型模型把输出预算烧在 `reasoning_content`(实测 16274 字)后,正文(6029 字)未写完就被网关 `finish_reason='length'` 截断。由于请求体不传 `max_tokens`,上限完全由厂商决定,无法在应用侧调高。

**解法**:把主请求从 1 次大请求拆成 5 次聚焦的小请求,逐步拼装 `rawText`,最后统一 `parse`。单步最大输出从 ~14000 字降到 ~3000-4500 字,推理模型撞上限的概率大幅下降。对外签名与后续流程(`completeIncompleteOutline` / `reviewAndFixOutline` / `repairChapterBlueprints`)**完全不变**。

## 5 步划分(默认,架构上可调粒度)

| 步 | 产出段 | 依赖 | 估算输出 | 失败处理 |
|----|--------|------|----------|----------|
| 1 设定层 | 故事定位+核心驱动+金手指+故事规模+四幕+世界与势力 | seed/direction | ~1500字 | 无兜底,重试耗尽→throw(触发整体重试) |
| 2 卷纲 | 卷纲(动态卷数) | 第1步 | ~300-3000字 | 无兜底,重试耗尽→throw |
| 3 启动包 | 前50章启动包(10个5章块) | 第1+2步 | ~1500-2500字 | 无兜底,重试耗尽→throw |
| 4 角色+伏笔 | 关键角色规划+伏笔规划 | 第1步 | ~3000-4500字 | 重试耗尽→跳过,由现有 `completeIncompleteOutline` 兜底补全 |
| 5 节奏包装 | 主要支线+故事线+情绪爽点+卖点承载 | 第1步 | ~1500字 | 重试耗尽→跳过(软字段,缺失不影响 `canApply`) |

> 架构上步骤定义为数据驱动的数组,若实测第4步(角色+伏笔)仍偏大,可一行配置拆成"角色"/"伏笔"独立两步(变6步),无需改编排器。

### 1. `expand-direction-prompt.ts` — 抽取段模板为可复用常量

- 抽出**共享格式规则** `SHARED_FORMAT_RULES`(671-704行"额外规则"中与输出格式相关的部分)

### 2. 新建 `prompts/system/expand-direction-steps.ts` — 分步 prompt builder

5 个 builder 函数,各自组合 `SHARED_PREAMBLE`(精简版)+ 对应段模板 + 步骤专属指令:

```
buildSkeletonStepPrompt({ seed, direction, wordCountRange, enhancementBrief })
  → system: SHARED_PREAMBLE + 6个设定段模板 + "只输出这些段"指令
  → user: seed + direction + 规模换算 + enhancementBrief

buildVolumePlanStepPrompt({ contextRawText, direction, wordCountRange })
  → system: 精简前导 + 卷纲段模板(含动态卷数) + "只输出卷纲" + "卷数须与建议一致"
  → user: 【已确定方案】(第1步的设定层段原文) + direction

buildStartupStepPrompt({ contextRawText, direction })
  → system: 精简前导 + 启动包段模板(含10块模板) + 开篇钩子/必出事件/区块密度硬约束 + "只输出启动包"
  → user: 【已确定方案】(设定层+卷纲段) + direction

buildCastStepPrompt({ contextRawText, direction })
  → system: 精简前导 + 角色段+伏笔段模板 + "主角姓名须与设定一致" + "只输出这两段"
  → user: 【已确定方案】(设定层段,含主角姓名) + direction

buildRhythmStepPrompt({ contextRawText, direction })
  → system: 精简前导 + 支线/故事线/情绪/卖点段模板 + "只输出这些段"
  → user: 【已确定方案】(设定层+卷纲段) + direction
```

上下文传递:用现有 `extractOutlineSectionBody(rawText, aliases)` 只提取相关段(避免传整份累计文本膨胀)。复用 `buildScaleGuidance` / `buildVolumePlanSection` / `buildStartupBlockSection` 现有函数。

### 3. 新建 `generators/outline-stepper.ts` — 分步编排器

```
export async function generateExpandedOutlineInSteps(params: {
  seed, direction, options, enhancementBrief?,
  callStructuredTextMode: StructuredTextCaller,  // 注入(同 completer 模式)
  runWithRetry: <T>(...) => Promise<T>,           // 注入步级重试
  onProgress?: (msg) => void,
}): Promise<{ rawText: string; warnings: string[] }>
```

核心逻辑:
1. 逐步执行:每步 `callStructuredTextMode(system, user, opts, 'outline-expand')` → `extractOutlineSectionBody` 取出该步段正文 → `replaceOutlineSection` 拼到累计 `rawText`
2. **步级重试**:每步用 `runWithRetry`(maxAttempts=2)单独包裹,失败处理见上表
3. **进度透传**:每步开始时 `onProgress?.('正在生成...')`
4. 返回拼装完整的 `rawText`(含全部段),供外层 `parseExpandedOutline` + 后续流程消费

复用现有工具:`replaceOutlineSection` / `extractOutlineSectionBody`(`outline-completer.ts:71-110`)、`runWithRetry`(`unified-generator.ts:705`)。

### 4. 修改 `unified-generator.ts` — `expandDirection` 接入分步

仅替换主请求部分(`unified-generator.ts:506-516`):

```
// 旧:
const builtPrompt = buildExpandDirectionPrompt({...});
onProgress?.('正在展开主方案...');
let rawText = await this.callStructuredTextMode(builtPrompt.system, builtPrompt.user, opts, 'outline-expand');
let outline = parseExpandedOutline(rawText);

// 新:
const { rawText, warnings: stepWarnings } = await generateExpandedOutlineInSteps({
  seed: prompt, direction, options: opts, enhancementBrief: opts.enhancementBrief,
  callStructuredTextMode: (system, user, callOpts) => this.callStructuredTextMode(system, user, callOpts, 'outline-expand'),
  runWithRetry: (run, isSuccess, maxAttempts, onProg, baseTemp) => this.runWithRetry(run, isSuccess, maxAttempts, onProg, baseTemp),
  onProgress,
});
let rawText = stepText;
let outline = parseExpandedOutline(rawText);
warnings.push(...stepWarnings);
```

**后续流程完全不变**:`completeIncompleteOutline`(528行)→ `reviewAndFixOutline`(557行)→ `repairChapterBlueprints`(581/631行)原样保留。外层 `runWithRetry`(499行)的成功判定 `result.outline !== null && !result.severelyTruncated`(679行)也不变。

## 不变的部分

- 对外签名:`expandDirection` 返回 `ExpandedOutlineResult`,composable `useOutlineGenerator` 和 3 个 UI 调用方(`TopicDiscoveryBoard` / `QuickStart` / `ProOutliner`)**零改动**
- 请求体仍**不传 `max_tokens`**(尊重"按需配置"原则)
- `parseExpandedOutline` 段级解析逻辑不变(分步拼装的 rawText 格式与一次性产出完全一致)
- 单章蓝图仍由 `completeIncompleteOutline` 分批生成(主方案始终不产出单章蓝图)
- 完整性门禁 `inspectOutlineCompleteness` / `hasStructuralOutlineBlockers` 不变

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 分步产出的段名/子结构不匹配 parser | 段模板从现有 SYSTEM_PROMPT **原样抽取**(非重写);每步 prompt 强调"只输出指定段,用精确段名";`parseExpandedOutline` 对缺段本就容错 |
| 步骤间不一致(如角色姓名与设定层主角不符) | 后续步骤上下文含设定层"核心驱动"段(含主角姓名);prompt 明确"须与已确定方案一致" |
| 上下文随步骤膨胀 | 用 `extractOutlineSectionBody` 只传相关段,非整份累计 rawText |
| 延迟增加(5次 vs 1次) | 每次输出量小、更快;成功率从"经常失败"到"基本成功"是主要收益;步骤定义数据驱动,可按需合并/拆分 |
| 卷数极多时第2步卷纲仍偏大 | 卷纲单独成步已是最大隔离;若仍截断,可在编排器里对卷纲做"分卷批生成"(复用 `repairChapterBlueprints` 的分批模式)作为后续增强 |
