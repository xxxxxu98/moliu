# 批量续写稳定性改造计划（P0–P2 全量）

## 一、根因与策略（一句话回顾）

单章失败被无差别重试 3 次 → `shouldStop` 停整批；stream 路径无 SDK 级重试；schema 硬校验缺字段即崩；draft 已生成却被 extract 失败连带作废。**策略：错误分级 → 跳过失败而非停整批 → stream/schema/步骤级三层兜底 → Chapter 状态字段持久化失败标记 + 失败队列补写。**

## 二、数据结构变更（先行，影响后续所有改动）

### 2.1 新增 `src/renderer/src/utils/ai-error-classify.ts`（新文件）
导出错误分类工具，作为 P0/P1/P2 的共用基础。复用并提升现有正则 `isTransientAiError`（`src/renderer/src/services/writing/__tests__/realStructuredAI.ts:36-44`）和 `ContinuityValidator.ts:309-313`。

```ts
export type ErrorKind =
  | 'network'      // fetch failed / ERR_CONNECTION_CLOSED / ECONNRESET / TypeError(fetch)
  | 'timeout'      // AbortError 且 signal.aborted === false（超时护栏触发）
  | 'truncated'    // JSON 截断 / 解析失败
  | 'schema'       // "结构校验失败:" / zod 报错
  | 'review'       // "严格门禁未通过" / "严格连续性门禁未通过"
  | 'wordcount'    // "字数严重不足" / "word-count-short:"
  | 'rate_limit'   // 429
  | 'server'       // 5xx
  | 'auth'         // 401/403
  | 'provider'     // 400/404 等业务 4xx
  | 'aborted'      // signal.aborted === true（用户主动停止）
  | 'unknown';

export interface ClassifiedError {
  kind: ErrorKind;
  retryable: boolean;   // 是否值得在批量层重试整章
  transient: boolean;   // 是否值得在 AI 调用层/管道层细粒度重试
}

export function classifyError(err: unknown, signal?: AbortSignal): ClassifiedError;
```

**分类规则**（基于已收集的消息模式）：
| kind | retryable（整章） | transient（细粒度） | 判定依据 |
|---|---|---|---|
| network/timeout/truncated/rate_limit/server | ✅ | ✅ | 瞬态，重试大概率成功 |
| schema | ❌ | ❌ | 持久（但 P1 软化后大幅减少） |
| review/wordcount | ❌ | ❌ | 管道内已 rewrite 2 轮，到批量层视为定局 |
| auth/provider | ❌ | ❌ | 配置/配额问题，重试无用 |
| aborted | ❌ | ❌ | 用户意图，立即停 |

检测点：`err instanceof Error && err.name === 'AIError'` → 读 `(err as any).status`（网络错误反而是原生 `TypeError`，无 status）；message 命中已收集的关键词前缀（`结构校验失败:`、`无法解析 AI 返回的 JSON`、`AI 返回的结构化 JSON 无法解析`、`严格门禁未通过`、`严格连续性门禁未通过`、`字数严重不足`）。

### 2.2 扩展 `ChapterWriteOutput`（`ChapterWritingPipeline.ts:163-184`）
新增两个可选字段（不破坏 `smartContinue.ts` / `WritingOrchestratorV2.ts` 等现有调用方）：
```ts
errorKind?: ErrorKind;
retryable?: boolean;
```
管道各 `fail()` 出口（`:397/:480/:510/:688/:731`）和 `executeChapterWriting` 的 throw 点按来源填值。

### 2.3 扩展 `Chapter` 类型（`src/renderer/src/types/project.ts:180-195`）
新增状态字段，随 `projectStore` 持久化（electron-store）：
```ts
writeStatus?: 'pending' | 'writing' | 'success' | 'failed';
lastError?: string;        // 最近一次失败原因（用于 UI 红标 + tooltip）
lastErrorKind?: ErrorKind;
lastErrorAt?: string;      // ISO 时间戳
```
- `createChapter`（`project.store.ts:153-174`）默认 `writeStatus: 'pending'`。
- 成功提交后（`useBatchWriter` 写 content 时）置 `success`。
- 批量内"正在写"置 `writing`（可选，纯 UI 增强）。
- 失败耗尽置 `failed` + `lastError`。

## 三、P0 — 立即止血

### P0-1 错误分级重试（核心）
**改动文件**：`src/renderer/src/composables/useBatchWriter.ts`

1. `config.value.maxRetries`（`:560`）默认 `3 → 5`（瞬态错误吃更多预算）；UI `BatchWritingPanel.vue:784-791` 的 NInputNumber 上限 `5 → 8`。

2. 重写重试循环 `:977-1029` 的 catch（`:1004-1018`）：
   - 调 `classifyError(err, internalState.abortController?.signal)`；
   - `kind === 'aborted'` → 立即 `shouldStop=true; break`（尊重用户停止）；
   - `retryable === false`（持久）→ 不退避、直接判定本章失败，跳出 attempt 循环进 P0-2 的跳过逻辑；
   - `retryable === true`（瞬态）→ 计入 attempt，**指数退避改为更长**：`4/8/16/30/30s`（现 `2^attempt` 太短），退避期间响应暂停。

3. `executeChapterWriting` 的 throw 点（`:755-771`）：读取 `result.errorKind / result.retryable`（来自 2.2），透传到 `WritingError` 的 `details`（`new WritingError(msg, code, { details: { errorKind, retryable } })`），catch 里优先用 details 里的分类（管道层判定更准），fallback 到 message 分类。

4. `registerFailure`（`:761-766`）：当前硬编码 `step='draft'`，改为透传 `errorKind` 到 `metadata`，供 UI 汇总分类展示。

### P0-2 单章耗尽 → 跳过而非停整批
**改动文件**：`useBatchWriter.ts` + `BatchWritingPanel.vue` + `project.store.ts`

1. 批量循环新增 `failedChapters: { index, id, title, error, errorKind, attempts }[]`（内存）。

2. 改 `useBatchWriter.ts:1025-1029`：
   ```ts
   // 旧：shouldStop = true; break;
   // 新：
   failedChapters.push({ index: currentIndex, id: chapter.id, title: chapter.title, error: chapterLastErr, errorKind, attempts: chapterMaxRetries });
   // 标记 Chapter 状态字段
   projectStore.updateChapter(chapter.id, { writeStatus: 'failed', lastError: chapterLastErr, lastErrorKind: errorKind, lastErrorAt: new Date().toISOString() });
   continue;   // 继续下一章，不停整批
   ```

3. **更新 `getNextChapterIndex`（`:615-623`）**：跳过逻辑改为「content 为空 **且** `writeStatus !== 'failed'`」。这样批量重启时自动跳过已知失败章，不会原地反复重试同一个坏章（除非用户走 P2 的"重试失败"入口显式清状态）。

4. **批量结束汇总**：`startBatchWriting` 的 finally（`:1042-1051`）新增 `batchSummary` ref（`{ total, written, failed: failedChapters, stopped: boolean, durationMs }`），通过新增的 `onBatchComplete` 回调或暴露 ref 供面板消费。

5. **UI**（`BatchWritingPanel.vue`）：
   - 章节 list（`:856-892`）样式增加 `writeStatus==='failed'` 分支：红底 + AlertCircle + tooltip 显示 `lastError`（当前失败章和未写过无法区分）。
   - 面板底部新增"批量完成"汇总卡（`watch(isWriting)` 由 true→false 触发）：显示成功 N 章 / 失败 M 章 + 失败清单 +「重试失败章节」按钮（接 P2-3）。

### P0-3 stream 路径内层重试（根因层）
**改动文件**：`src/renderer/src/services/ai/unified.service.ts`

1. 抽取 stream catch（`:354-386`）为内部方法 `streamOnce(messages, opts, signal)`。

2. 新增 `streamWithRetry`：对**非 abort** 的 `TypeError(fetch)` / `AIError(status undefined || >=500 || ===429)` / 流中断（content 异常短）做 1–2 次内部重试，退避 `1/2s`（参考 SDK `withRetryAndFallback` 的 `1e3*2**(o-1)`）。
   - **关键**：仅在 `signal.aborted===false` 时重试；abort 立即抛 `DOMException('Aborted')`。
   - 4xx（含 400 response_format 拒绝）已有降级先例（`:1091-1114`），保留不动。

3. **可选 SDK 层（标注为后续优化）**：若 multi-ai-sdk 后续可改，让 `stream()` 复用 `withRetryAndFallback`，则应用层重试可简化。本轮先走应用层（SDK 是压缩的第三方产物，应用层足够止血）。

### P1-2 管道内步骤级重试
**改动文件**：`src/renderer/src/services/story-runtime/LongFormWritingEngine.ts`

1. 重写 `write()` 的 `while(true)`（`:165-227`），把步骤分组并加细粒度重试：
   - **Step A（draft+pad，`:166-172`）**：单独 try/catch，失败按 `classifyError` 判定；瞬态重试最多 2 次（退避 2/4s），持久或耗尽 → 冒泡（带 errorKind）。
   - **Step B（extract+canonicalize+validate，`:174-194`）**：**保留 Step A 已生成的 `drafts`**，单独 try/catch；extract 瞬态失败重试最多 2 次，drafts 不作废（当前痛点：draft 已花钱却因 extract 失败丢弃）。

2. 参照现有 `supplementDraftsWhileShort` 的 `consecutiveFailures + MAX_SUPPLEMENT_ATTEMPTS=3`（`:396-409`）模式实现步骤级重试计数。

3. 最终失败时通过 `ChapterWriteOutput.errorKind/retryable`（2.2）把分类信息传给批量层，让 P0-1 据此决策。

## 九、风险与回滚

- **风险 1**：getNextChapterIndex 改为跳过 `failed` 章后，旧的"重试整批"行为变化——靠 P2-3 的显式"重试失败"入口兜底，且首次跳过的失败章会通过 UI 汇总明确提示。
- **风险 2**：schema 软化可能掩盖模型返回退化——靠 `console.warn` + 可观测，不静默吞。
- **风险 3**：步骤级重试可能掩盖管道真实 bug——重试仅对 transient 错误，持久错误立即冒泡。
- **回滚**：所有改动为加法（新可选字段、新分支、新文件），可按里程碑逐级回滚；P1/P2 不依赖 P0 之外的前置，可独立关闭。
