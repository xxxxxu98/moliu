## P0 · 缺陷4：思考链/安全审查块泄露进正文（最高优先级，生产硬伤）

**根因**：AI（deepseek）在 supplement 补写轮返回非法 JSON，`<think>`/`<ds_safety>` 等推理/安全标签 + JSON 残片 `"}]}。{` 被 `jsonrepair`（`json-parser.ts:118/167`）当成合法字符串吸收进 `paragraphs[]`，最终拼进正文。现有 `stripDraftLeakage.ts` 只剥结构骨架（`STRUCTURAL_KEYS`/孤立括号），不识别这些标签。

**双层修复：**

### 层1（根本）：`src/renderer/src/utils/json-parser.ts`
在 `robustJsonParse` 第 36 行（前缀清洗）之后、任何 jsonrepair 策略之前，注入一个剥离步骤：删除成对推理/安全标签及其内容，以及未闭合标签到结尾的内容。

新增模块内函数：
```ts
/** 剥离推理/安全审查 meta 标签（deepseek-r1 的 <think>、deepseek 的 <ds_safety> 等）。
 *  这些标签是模型 meta 输出，绝非合法 JSON 内容；在 jsonrepair 之前剥掉，
 *  避免 jsonrepair 把标签后的思考链/残片当成字符串值吸收。 */
function stripReasoningAndSafetyTags(input: string): string {
  return input
    // 成对标签（含内容）：<think>...</think> / <ds_safety>...</ds_safety> / <reflection>...</reflection>
    .replace(/<(think|ds_safety|reflection|reasoning|analysis)>\s*[\s\S]*?<\/\1>\s*/gi, '')
    // 未闭合/截断标签到结尾（模型被截断时常出现）：从标签开始删到字符串末尾
    .replace(/<(think|ds_safety|reflection|reasoning|analysis)>[\s\S]*$/gi, '')
    .trim();
}
```
在第 36 行后调用：`content = stripReasoningAndSafetyTags(content);`

**安全性论证**：这些标签在任何合法 AI JSON 响应中都不会作为数据出现；剥离是纯增益，不影响任何合法解析路径。

### 层2（纵深防御）：`src/renderer/src/services/story-runtime/stripDraftLeakage.ts`
扩展 `sanitizeSceneDraftParagraphs`，对每个段落字符串内部剥离残留的 `<think>`/`<ds_safety>` 片段 + 段末 JSON 残片（如 `"}]}。{`、`}。ăn`）。即使层1漏网（或未来出现新型标签），下游兜底。

新增模块内正则辅助：
```ts

const REASONING_FRAGMENT_RE = /<\s*(?:think|ds_safety|reflection|reasoning|analysis)\b[^>]*>[\s\S]*$/i;
```

在 `sanitizeSceneDraftParagraphs` 的逐段循环里，于 `stripTrailingJsonClosers` 之后增加：剥推理碎片 → 若段尾出现中文标点紧跟括号再跟非中文杂质的模式，截断到中文标点处。

### 单测：新建 `src/renderer/src/services/story-runtime/__tests__/stripDraftLeakage.leak.test.ts`
覆盖：(a) 含 `<ds_safety>` 的段落被截净；(b) 段末 `议论声如沸鼎。"}]}。{` 被清洗为 `议论声如沸鼎。`；(c) 干净正文不被误伤。

## P1 · 缺陷1：goal 字段被「结构化节点」块污染

**根因**：`useChapterOutlineGenerator.ts:543-554` 建章时把 `--- 结构化节点 ---\n【CBN】...` 块拼进 `chapter.outline`；`ChapterWritingPipeline.executeLongFormRuntime` 的 `:633`(description)/`:657`(goal)/`:671`(query) 把 `input.chapter.outline` 原样当 goal，导致 scene-draft prompt 的 `locked-contracts.chapter.goal` 是一大段结构化节点而非简洁目标。

**方案：消费端清洗（不动源头，保留 UI 完整展示 outline）。** 结构化节点已通过 `outlineNode` 的 CBN/CPNs/CEN 独立字段传递，outline 里那份是冗余污染。

### 新增工具函数：`src/renderer/src/services/outline/parser/utils.ts`
```ts
/** 剥离 outline 末尾的「--- 结构化节点 ---」块（CBN/CPNs/CEN/mustCover/forbiddenZones）。
 *  useChapterOutlineGenerator 建章时把结构化节点拼进了 outline 字段，
 *  而 executeLongFormRuntime 把 outline 当 goal/description，污染了写作 prompt。
 *  这里剥掉该块，只保留散文大纲。无标记则原样返回。 */
export function stripStructuredNodeBlock(outline: string): string {
  if (!outline) return '';
  return outline.replace(/\n*---\s*结构化节点\s*---[\s\S]*$/u, '').trim();
}
```

### 消费：`src/renderer/src/services/writing/ChapterWritingPipeline.ts` `executeLongFormRuntime`
在 `outlineNode` 构造前（约 630 行）新增：
```ts
const cleanOutline = stripStructuredNodeBlock(input.chapter.outline || '');
```
三处替换 `input.chapter.outline` → `cleanOutline`：
- `:633` `description: cleanOutline || input.chapter.plotSummary || ''`
- `:657` `goal: cleanOutline || input.chapter.plotSummary || input.chapter.title`
- `:671` `query: taskBook?.CPNs.join(' ') || cleanOutline || input.chapter.plotSummary || input.chapter.title`

### 单测：扩展 outline parser 测试
覆盖：`stripStructuredNodeBlock('散文\n\n--- 结构化节点 ---\n【CBN】xx')` → `'散文'`；无标记原样返回。

## P2 · 缺陷2：CPNs 解析错乱（编号列表不识别）

**根因**：`parser/utils.ts:80` `extractMultiValueField` 只按标点 `；；、，，/` 切；`extractFieldValue` 经 `compactLines` 把多行编号列表拍平成一行，导致 `"1. xxx 2. yyy"` 的编号 `2.` 串到前一项。是否出错取决于 AI 当次是否返回 `数字.` 编号格式——间歇性不稳定。

**方案：`extractMultiValueField` 优先按编号列表解析，保留换行不拍平。** 不动 `extractFieldValue`/`compactLines`（其他字段依赖其拍平行为）。

### 修改：`src/renderer/src/services/outline/parser/utils.ts`
新增编号列表解析 + 改造 `extractMultiValueField`：
```ts
/** 从 block 中提取某字段下的「数字. 内容」编号列表项，保留多行结构。
 *  AI 常把 CPNs/mustCover 写成 `1. xxx\n2. yyy`，extractFieldValue 的 compactLines
 *  会把它们拍平成一行 `1. xxx 2. yyy`，导致编号串到前一项。这里直接从原始 block 解析。 */
function extractNumberedItems(block: string, fieldName: string): string[] {
  const escaped = escapeRegExp(fieldName);
  // 字段行：`CPNs：` 或 `- CPNs：`，之后跟编号列表
  const fieldPattern = new RegExp(
    `^(?:-\\s*)?${escaped}\\s*[：:]\\s*$([\\s\\S]*?)(?=\\n(?:-\\s*)?[^[\\n：:]{0,20}[：:]|\\n---|$)`,
    'm'
  );
  // 简化：找字段行后到下一个字段/分隔符之间的 body
  const lines = block.split('\n');
  const startIdx = lines.findIndex(l => new RegExp(`^(?:-\\s*)?${escaped}\\s*[：:]`).test(l.trim()));
  if (startIdx === -1) return [];
  const items: string[] = [];
  const itemStart = /^\s*(\d+)[.、)]\s*(.+)$/;
  const fieldStart = /^(?:-\s*)?[^\s：:][^：:]{0,20}\s*[：:]/;
  let currentItem: string | null = null;
  for (let i = startIdx + 1; i < lines.length; i++) {
    const line = lines[i].trim();
    if (line === '' || line.startsWith('---')) break;
    if (fieldStart.test(line)) break;
    const m = line.match(itemStart);
    if (m) {
      if (currentItem) items.push(currentItem.trim());
      currentItem = m[2];
    } else if (currentItem !== null) {
      currentItem += ' ' + line; // 编号项续行
    }
  }
  if (currentItem) items.push(currentItem.trim());
  return items.filter(Boolean);
}

export function extractMultiValueField(block: string, fieldName: string): string[] {
  // 优先：编号列表（AI 常用 1./2./3. 格式，compactLines 会破坏它）
  const numbered = extractNumberedItems(block, fieldName);
  if (numbered.length > 1) {
    return numbered
      .flatMap(item => item.split(/[；;、，,/]/)) // 单项内可能仍有顿号/逗号并列
      .map(s => s.trim()).filter(Boolean)
      .filter((item, i, arr) => arr.indexOf(item) === i);
  }
  // fallback：原有标点切分逻辑
  const value = extractFieldValue(block, fieldName);
  if (!value) return [];
  return value.split(/[；;、，,/]).map(s => s.trim()).filter(Boolean)
    .filter((item, i, arr) => arr.indexOf(item) === i);
}
```

### 单测：扩展 outline parser 测试
覆盖：(a) `1. A\n2. B\n3. C` → 3 个独立项；(b) 单行逗号并列 `A，B，C` 仍走 fallback 正常切；(c) 续行 `1. 第一行\n续行内容\n2. 第二行` 正确归并。

## P3 · 缺陷3：章节标题回写断裂（forceStoryRuntime 下 title 全 null）

**根因**：`ChapterWritingPipeline.ts:760-767` 回填被 `shouldApplyGeneratedTitle`（仅占位标题 true）门控；forceStoryRuntime 下 `readBackTitle`（:953）恒返回 null。续写 AI 明明产出了 `chapterTitle`（如"太子送来的密信"），但 `output.title` 为 null。

**方案：最小改动——回填兜底从 `null` 改为保留原标题。** 不动 `readBackTitle` 的 forceStoryRuntime 短路（避免引入风险），只让"非占位标题"分支回填 `input.chapter.title` 而非 null。

### 修改：`src/renderer/src/services/writing/ChapterWritingPipeline.ts`
成功分支（`:760-767`）的 title：
```ts
title:
  this.readBackTitle(input.chapter.id) ??
  (shouldApplyGeneratedTitle && generatedShortTitle
    ? `第${chapterNumber}章 ${generatedShortTitle}`
    : input.chapter.title ?? null),
```
失败分支（`:724-726`）同样补 `input.chapter.title ?? null` 兜底。

**效果**：真实 App（非 forceStoryRuntime）`readBackTitle` 优先读 store 短标题，行为不变；冒烟/harness（forceStoryRuntime）下 title 不再是 null，保留建章时的真实标题。

## 影响面与风险评估
- **json-parser.ts（P0层1）**：通用工具，但剥离的标签在合法 JSON 中不会出现，零副作用。
- **stripDraftLeakage.ts（P0层2）**：仅追加清洗规则，干净正文经现有测试验证不受影响。
- **stripStructuredNodeBlock（P1）**：仅消费端，UI 的 outline 展示完全不变。
- **extractMultiValueField（P2）**：编号列表优先，无编号时 fallback 原逻辑，向后兼容。
- **title 回填（P3）**：仅在 null 兜底处补原标题，真实 App 路径不受影响。
